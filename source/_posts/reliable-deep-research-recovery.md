Reliable Deep Research 以研究任务为单位保存执行结果。重启后复用已经提交的结果，未完成的尝试重新执行。本文说明任务状态和证据如何处理，以及合成故障实验的结果。

## 状态存储

运行时把研究过程组织成有界 DAG，并通过 SQLite 保存任务结果和证据。依赖任务读取已经提交的上游结果，调度器负责失败重试和任务重放。

这里“已完成”需要有持久化提交作为依据。进程内函数返回过一次，并不等于下次启动时一定存在可复用的结果。

## 旧证据清理

一个任务尝试可能已经写入部分证据，随后失败。直接重新执行而不处理残留，会让旧结果混入新的报告。

因此，恢复过程除了判断任务状态，还需要清理未完成尝试留下的过期 Evidence/Claim，避免报告环节继续使用已经失效的内容。

## 故障实验

| 实验场景 | 发布结果 |
| --- | --- |
| 短暂异常 | 30/30 次恢复 |
| 超时 | 30/30 次恢复 |
| 任务提交后真实进程退出 | 20/20 次重启复用已完成任务，未重复执行该任务 |
| 未完成尝试后重启 | 验证旧 Evidence/Claim 清理 |

这些是独立的合成故障实验。它们验证了指定条件下的恢复行为，不等同于证明任意线上故障下都能恢复。

完整协议与结果入口见 GitHub 上的[恢复实验文档](https://github.com/hilzlzl/reliable-deep-research/blob/main/docs/evaluation.zh-CN.md#任务恢复实验)。

## 恢复边界

**研究任务恢复并不等于整个 LangGraph 会话恢复。** 运行时复用的是已提交的任务结果，而不是任意时刻的全部进程状态。

它也不保证外部 API 恰好执行一次。如果外部调用完成后、本地结果提交前进程退出，下次重试仍可能再次调用外部服务。

对于具有外部副作用的工具，仍需要结合服务端幂等键或业务去重设计。对于检索与模型调用，也应把可能重复发生的费用纳入预算考虑。

## 本地演示

项目提供不需要密钥的演示：

```bash
uv sync --frozen --python 3.11 --extra dev
uv run --frozen python -m experiments.reliability.reliability_demo
```

运行后查看 `artifacts/reliability_demo/` 中的结果、事件轨迹和 SQLite 数据库，可以对照理解一次失败、一次重试和一次结果复用。
